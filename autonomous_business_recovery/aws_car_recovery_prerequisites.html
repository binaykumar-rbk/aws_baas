AWS cloud applications recovery prerequisites

You must fulfill specific prerequisites in RSC and in the AWS Management Console before recovering a cloud application, so that the recovery operation does not fail because of a missing permission, key, certificate, or external resource in the recovery account.

An AWS cloud application recovery re-creates the application in a separate recovery AWS cloud account. RSC provisions the configuration resources and exports the workload snapshots from the most recent backup in application. However, some external dependencies, such as KMS keys, ACM certificates, and SSH key pairs, are not replicated automatically and must already exist in the recovery account with the same identifiers.

You can use the following table to verify each prerequisite and address any gaps before starting the recovery.
Prerequisite Description Action
Recovery AWS cloud account A separate AWS cloud account must be configured in RSC as the recovery account, with both the Basic and Recovery permission categories of the Cloud Applications feature enabled under Manage Granular Permissions. RSC creates and configures resources in this account during recovery. Configuring the recovery account if not already set up. For more information, see Adding a recovery account for Autonomous Business Recovery.
EC2, RDS, and S3 features enabled in the recovery account The EC2, RDS, and S3 features must be enabled on the recovery account with the recovery permissions so that RSC can export EC2 instances, RDS databases, and S3 buckets from the snapshots into the recovery account. Enabling the EC2, RDS, and S3 features on the recovery account in RSC. For more information, see Edit an AWS account.
Application snapshot The cloud application must have at least one available snapshot that includes both configuration resource metadata and workload data. A complete snapshot is required to initiate recovery. Verifying on the Snapshots tab of the Cloud Application page that a snapshot is available. If no snapshot is available, you must wait for the next backup cycle.
RSC Recovery permission You must have a RSC user role with the Recovery permission on the AWS cloud account to initiate a recovery from the recovery wizard. Verifying your role permissions. For more information, see RSC user permissions for AWS cloud application.
Key Management Service (KMS) keys for application resources KMS keys that are part of the source application must be present in the recovery account with the same alias before you initiate recovery. These keys are used by EBS volumes, RDS databases, and other encrypted resources. If a KMS key with the matching alias is not found in the recovery account, the recovery of resources that depend on that key will fail. RSC never creates, imports, or modifies KMS keys in the recovery account. It validates only that a key with the matching alias exists, and does not validate the key policy. You are responsible for ensuring that the key policy allows the services and roles that use the key. If the source application uses a KMS key that is shared from another account, share the key with the recovery account as well. Creating a KMS key with the matching alias in the recovery account, and ensuring that its key policy is correct. For more information, see Creating keys in the AWS documentation.
KMS key policy for Secrets Manager, ElastiCache, and Auto Scaling The KMS key policy in the recovery account must allow the principals that create and use the encrypted resources. Without these permissions, recovery fails with KMS access denied errors.
  • Secrets Manager and ElastiCache: The Rubrik cross-account role creates the encrypted secrets and ElastiCache clusters. The key policy must allow this role to use the key through the Secrets Manager and ElastiCache services. Add the following statement to the key policy. Replace ACCOUNT-ID, RUBRIK-ROLE-NAME, and REGION with your values.
    {
  "Sid": "AllowRubrikRoleUseOfKeyViaElastiCacheAndSecretsManager",
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::<ACCOUNT-ID>:role/<RUBRIK-ROLE-NAME>"
  },
  "Action": [
    "kms:Encrypt",
    "kms:Decrypt",
    "kms:ReEncrypt*",
    "kms:GenerateDataKey*",
    "kms:CreateGrant",
    "kms:DescribeKey"
  ],
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "kms:ViaService": [
        "elasticache.<REGION>.amazonaws.com",
        "secretsmanager.<REGION>.amazonaws.com"
      ]
    }
  }
}
  • Auto Scaling: Auto Scaling launches EC2 instances with encrypted EBS volumes. The key policy must allow the Auto Scaling service-linked role to use the key and to create grants for the volumes. Add the following statements to the key policy. Replace ACCOUNT-ID with your account ID.
    {
  "Sid": "AllowAutoScalingUseOfKey",
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::<ACCOUNT-ID>:role/aws-service-role/autoscaling.amazonaws.com/AWSServiceRoleForAutoScaling"
  },
  "Action": [
    "kms:Encrypt",
    "kms:Decrypt",
    "kms:ReEncrypt*",
    "kms:GenerateDataKey*",
    "kms:DescribeKey"
  ],
  "Resource": "*"
},
{
  "Sid": "AllowAutoScalingAttachmentOfPersistentResources",
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::<ACCOUNT-ID>:role/aws-service-role/autoscaling.amazonaws.com/AWSServiceRoleForAutoScaling"
  },
  "Action": [
    "kms:CreateGrant",
    "kms:ListGrants",
    "kms:RevokeGrant"
  ],
  "Resource": "*",
  "Condition": {
    "Bool": {
      "kms:GrantIsForAWSResource": "true"
    }
  }
}
 Adding the required statements to the key policy of the matching KMS key in the recovery account. For more information, see Key policies in AWS KMS in the AWS documentation.
Encryption keys for AMI and EBS replication During backup, RSC replicates AMI snapshots from the source account to the recovery account. If source resources are encrypted, the recovery account must be able to decrypt and re-encrypt them. All replicated AMI snapshots are encrypted with an AWS-managed key in the recovery account.
  • If the source uses a Customer Managed Key (CMK), you must share the CMK with the recovery target account by updating the key policy.
  • If the source uses an AWS-managed key, you must create a customer-managed KMS key with the alias rk_cnp_encryption_key in the source account and share it with the recovery target account. AWS-managed keys cannot be shared across accounts.
  • AMIs not owned by the source account, such as public AMIs, AWS Marketplace AMIs, or AMIs shared from another account, are not replicated. These AMIs must be accessible in the recovery account for successful recovery. AWS Marketplace subscriptions apply to each AWS account, so you must also subscribe the recovery account to the Marketplace AMI. Similarly, share AMIs from a central account with the recovery account.
 Sharing the source CMK with the recovery account, or creating the rk_cnp_encryption_key CMK. For more information, see Allowing users in other accounts to use a KMS key in the AWS documentation.
ACM certificates ACM certificates used by application resources such as load balancers must be present in the recovery account with the same domain name before you initiate recovery. RSC references ACM certificates by domain during recovery. If a matching certificate is not found, load balancer listener configuration will fail. Requesting or importing a certificate with the same domain in the recovery account. For more information, see Issuing and managing certificates in the AWS documentation.
SSH key pairs SSH key pairs used by the source EC2 instances must be present in the recovery target account with the same name. During recovery, RSC launches EC2 instances using the source launch template, which references the key pair by name. If the key pair is not found, the instance recovery may fail. Importing the existing public key in the recovery account or creating a key pair with the same name in the recovery account. For more information, see Amazon EC2 key pairs in the AWS documentation.
RDS archived snapshot recovery prerequisites Recovery from an RDS archived snapshot requires network connectivity between Exocompute and the RDS database that is being recovered. If you select the Clone the source VPCs network option, RSC sets up this connectivity for you. If you select the Use already created VPCs from the recovery account network option, the target VPC must already exist in the recovery account and you must configure the network connectivity with the Exocompute VPC before you initiate recovery. Recovery from an RDS archived snapshot is not supported if these prerequisites are not in place. If you use the Use already created VPCs from the recovery account option, verify that the target VPC exists in the recovery account and that network connectivity with the Exocompute VPC is configured before initiating recovery from an archived RDS snapshot. For the network rules required for RDS database recovery, see the Inbound rule for RDS PostgreSQL database recovery section in Network rules for EKS node at VPC or firewall.
Exocompute in the recovery account If you recover EC2 or RDS archived snapshots, S3 buckets, Lambda functions, or Secrets Manager secrets, Exocompute must be configured and mapped in the recovery account. If you recover from RDS archived snapshots and select the Clone the source VPCs network option, you must also add the RECOVER RDS CONNECTIVITY permission group for the Exocompute feature in the Exocompute AWS account. RSC uses this permission group to set up temporary connectivity between Exocompute and the recovered RDS database. Configuring Exocompute for the recovery account, and adding the RECOVER RDS CONNECTIVITY permission group if you recover from RDS archived snapshots by using the Clone the source VPCs option.
Permission groups for recovered workloads The recovery permission groups for the Cloud Applications feature and for every workload that you recover must be added to the recovery AWS account. Adding the recovery permission groups for the workloads that you recover. For more information, see Permission categories for Autonomous Business Recovery.
S3 target bucket If you plan to recover S3 buckets using the Export option, the target bucket must already exist in the recovery account. RSC lists the existing buckets in the recovery account for you to select. With the Create New Bucket option, RSC creates the bucket in the recovery account. Creating the target bucket in the recovery account if you plan to export to an existing bucket. For more information, see Recovering an AWS cloud application to a recovery account.
Other external dependencies Some external resources are not replicated automatically by RSC, including additional KMS keys, ACM certificates, and third-party integrations. You must pre-create these resources in the recovery account before you start the recovery. Reviewing the resource inventory of the cloud application and creating any missing external dependencies in the recovery account beforehand.
