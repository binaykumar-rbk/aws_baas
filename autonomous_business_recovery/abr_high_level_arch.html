High-level architecture for Autonomous Business Recovery

A high-level architectural overview about how RSC protects and recovers AWS cloud applications, including configuration resources and workloads.

You can use the SLA Domain feature of Rubrik to protect your AWS cloud applications. RSC uses a dual-layer approach to protect your AWS cloud applications, protecting configuration resource metadata separately from workload data to enable comprehensive application-level recovery.

At a high level, RSC uses the following workflow to protect AWS cloud applications:
  1. AWS cloud account onboarding and permissions setup
  2. AWS cloud application addition and resource discovery
  3. AWS configuration resources backup
  4. Independent AWS workload backup
  5. AWS cloud application recovery

AWS Cloud account onboarding and permission setup

When you add your AWS cloud account to RSC with the Cloud Applications feature enabled:
  • Authentication: RSC uses IAM roles with cross-account trust to authenticate with your AWS account.
  • Permission setup: RSC receives permissions across multiple AWS services, including EC2 instances, RDS databases, S3 buckets, VPC, ELB, Auto Scaling, Route 53, IAM, KMS, Systems Manager, EKS, ECS, ECR, Secret Manager, ElastiCache, and Lambda, to discover, protect, and recover cloud application resources.
  • Recovery account configuration: You configure a separate AWS account as the target or recovery account, enabling RSC to replicate resources such as Amazon Machine Images (AMIs), EBS snapshots, and so on, and recreate resources during cyber recovery.

AWS cloud application addition and resource discovery

While adding an AWS cloud application,RSC discovers the resources that belong to your cloud application:
  • Tag-based discovery: You specify up to three tags in RSC that match the tags you have manually assigned to your EC2 instances, RDS databases, and load balancers in the AWS Management Console. RSC uses these tags to identify the resources that belong to the application.
  • Auto-discovery: RSC automatically identifies all configuration resources connected to your tagged EC2 instances, RDS databases, and load balancers by traversing the dependency graph. This includes the configuration-only resources, such as VPCs, subnets, security groups, auto-scaling groups, launch template versions, KMS keys, IAM roles and policies, Lambda functions, EKS and ECS clusters, ElastiCache, ECR repositories, Secrets Manager secrets, and other supported resource types.
  • Cloud application boundary: The discovered resources are scoped to a single AWS account and a single AWS region, defining the boundary of your cloud application.

AWS configuration resources backup

RSC captures and stores the metadata for configuration resources, such as VPC, ELB, Auto Scaling, and Route 53, using two sequential tasks:
  • Metadata backup: RSC captures the metadata of each configuration resource and stores in a secure Rubrik-managed cloud storage bucket.
  • Replicated backup: For each AMI snapshot referenced by a launch template, RSC replicates the resource from the source account to the recovery account. During this process, RSC re-encrypts these resources using a KMS key owned by the recovery account where applicable to ensure seamless recovery. RSC only replicates AMIs owned by the source account. RSC does not copy AMIs not owned by the source account, such as public AMIs, AWS Marketplace AMIs, or AMIs shared from another account. Instead, the recovered launch template references these AMIs directly.
Note:
The cloud application SLA Domain must have a minimum backup frequency of 6 hours.

Independent AWS workload backup

Workload protection is independent of the cloud application SLA Domain. The SLA Domain assigned to a cloud application protects only the configuration resources. This cloud application SLA Domain does not automatically apply to workloads such as EC2 instances, RDS databases, and S3 buckets. Each workload retains its own SLA Domain, which must be assigned separately.

For the cloud application to achieve Fully Protected status, the backup frequency of the SLA Domain for each workload must match or exceed the backup frequency of the cloud application SLA Domain. Rubrik recommends assigning workload SLA Domains that are at least as frequent as the cloud application SLA Domain to ensure that every configuration snapshot has a corresponding workload snapshot available for recovery.

AWS cloud application recovery

RSC provides comprehensive recovery capabilities for the complete cloud application:
  • Recovery point selection: You select a recovery point using various filters to identify clean configuration and workload snapshots. Filters are only applicable to workload snapshots.
  • VPC networking: You configure VPC settings in the recovery account, with options to clone the source VPCs, use an existing VPC, or specify alternate CIDR blocks.
  • Dependency-ordered recovery: RSC recovers configuration resources first in dependency order (networking before compute), then restores workloads, preserving the relationships between resources.
  • Post-recovery automation: You can configure pre-recovery and post-recovery Lambda functions and per-EC2 SSM scripts for additional configuration and validation.
  • Post-recovery actions: After recovery reaches a terminal state, such as successful, partial, or failed, you must choose one of the following two finalization actions:
    • Clean-up: Deletes all resources created during the recovery in the recovery account. Pre-existing resources in the recovery account are not affected. You must use this option for recovery testing where you want to verify the recovery process and then remove the recovered resources. You can run multiple clean-up attempts.
    • Lock recovery: Transfers full ownership of the recovered resources to you and marks the recovery as locked. You can use this option when you have verified that the recovered application is working correctly.
      Warning:
      After locking, you cannot automatically clean up the recovered resources using RSC. The lock recovery action is permanent and irreversible.
