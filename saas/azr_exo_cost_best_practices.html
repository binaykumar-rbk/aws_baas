Best practices for reducing Exocompute on Azure costs

Configuring your Azure network, storage, and cluster settings correctly can significantly reduce ongoing costs when using Exocompute on Azure for archiving and data protection operations.

Exocompute on Azure uses an Azure Kubernetes Service (AKS) cluster to perform high-volume data operations, including archiving to and retrieval from Azure Blob Storage. Several factors determine the total cost: how blob storage traffic is routed from AKS nodes, how many AKS clusters your organization runs across subscriptions, the maximum node count configured for each cluster, and the Azure Blob access tier selected for long-term retention. Configuring any of these factors incorrectly can result in avoidable ongoing charges.

Review the following guidance before you enable Exocompute on Azure in a production environment, and use it to audit an existing deployment that may be incurring avoidable costs.

Use Azure service endpoints or private endpoints for storage tiering

  • When to use a service endpoint: Service endpoints are free and route blob traffic over the Azure backbone directly from your AKS subnet to the storage account in the same region. They are the simplest way to eliminate NAT Gateway data processing charges. For more information about how to configure service and private endpoints for archival locations, see Private and service endpoints usage for Azure storage tiering.
  • When to use a private endpoint: Private endpoints assign a private IP address to the storage account within your VNet, making it inaccessible from the public internet. Use a private endpoint when the security policy of your organization requires private-only storage access, or when your network uses Azure Firewall as the outbound path. For more information about firewall rule requirements, see Firewall configuration for Exocompute on Azure.
Important:
If a NAT Gateway is the only outbound path from your Exocompute subnet to Azure Blob Storage, all archiving and retrieval data transfers are subject to NAT Gateway data processing charges. Configure a service endpoint or private endpoint before you enable Exocompute in a production environment to avoid unexpected costs.

Example: An organization protects 300 Azure virtual machines with daily backups. Snapshots that meet the archival threshold in the SLA Domain are tiered to Azure Blob Storage by the AKS cluster. Without a service or private endpoint, AKS nodes route all write traffic through the NAT Gateway, incurring a data processing charge on every gigabyte written to the archival location. Configuring a service endpoint on the Exocompute subnet routes that same traffic over the Azure backbone at no additional charge.

For more information about service endpoints and private endpoints, see Azure Virtual Network service endpoints (Microsoft Azure documentation) and Azure Private Link overview (Microsoft Azure documentation).

Use centralized Exocompute to reduce AKS cluster costs

Each localized Exocompute configuration runs its own AKS cluster, including dedicated compute nodes, in the subscription where your protected workloads reside. When multiple subscriptions have low-to-moderate backup volumes, each cluster must maintain a minimum number of active nodes during scheduled backup windows, incurring compute charges independently even when individual utilization is low.

Centralized Exocompute lets you designate a single host subscription to run one shared AKS cluster and map multiple application subscriptions to it. All backup, indexing, archiving, and recovery operations for the mapped subscriptions run in the shared cluster, which autoscales based on aggregate demand. For a comparison of the two deployment models, see Localized versus centralized Exocompute on Azure. For configuration steps, see Mapping Azure accounts to centralized Exocompute.

Tip:
If your organization protects workloads across three or more Azure subscriptions in the same region, evaluate the centralized model before configuring Exocompute individually for each subscription. The reduction in idle cluster node hours is greatest when individual subscription workloads are light and predictable.

Example: An organization protects workloads in four Azure subscriptions in the East US region. With a localized deployment, four separate AKS clusters run concurrently, each maintaining at least one worker node during the nightly backup window. Compute charges for four independent clusters run in parallel. With centralized Exocompute, a single AKS cluster in a dedicated host subscription handles jobs for all four subscriptions, scales up during peak hours, and scales down when jobs complete. The three application subscriptions require no AKS compute resources of their own.

Right-size the Exocompute maximum node count

RSC autoscales the AKS cluster between a minimum of one node and the configured maximum. The default maximum is 64 nodes. RSC dynamically selects the most appropriate virtual machine size from the recommended virtual machine families based on the available vCPU quota in the region. For more information about the virtual machine families and quota requirements, see Exocompute on Azure vCPU quota requirements. The maximum node count directly determines the vCPU quota you must have available. Configuring a higher maximum than your workload requires means you must hold proportionally more quota in reserve.

Maximum node count Recommended for
32 Subscriptions with a small number of protected virtual machines, infrequent archiving schedules, or low concurrent job volume
64 (default) Most production deployments with standard backup and archiving workloads
128 High-volume environments with large virtual machine fleets, frequent indexing, or high concurrent recovery demand
256 Very large-scale deployments requiring significantly higher vCPU quota

Increasing the maximum node count also requires confirming that the associated VNet subnet has sufficient available IP addresses to support additional nodes. For more information about the subnet sizing guidance, see IP address planning for Exocompute on Azure.

You can change the maximum node count in the RSC advanced Exocompute settings. For more information about updating the setting, see Updating advanced Exocompute settings for Rubrik clusters.

Note:
Increasing the maximum node count requires a proportionally higher vCPU quota. For example, a 64-node cluster using Standard_D8s_v4 nodes requires up to 512 vCPUs of quota in that virtual machine family. Increasing the maximum to 128 nodes requires up to 1,024 vCPUs. Confirm available quota in the Azure portal before increasing the maximum. For more information about requesting a quota increase, see Increase VM-family vCPU quotas (Microsoft Azure documentation).

Select an appropriate access tier for storage tiering

RSC supports writing archived data to different access tiers. Selecting the appropriate tier for your planned retention period balances storage cost against retrieval time and frequency. You configure access tiers within RSC when creating an archival location and not through Azure-native tools such as Azure Storage lifecycle management policies. For more information about all available archival options, see Evaluate Azure storage tiering options. For a detailed comparison of Azure Blob access tiers, see Azure access tiers.

CAUTION:
Do not change the Azure Blob access tier for Rubrik-archived data outside of RSC. Modifying access tiers directly in the Azure portal or through Azure Storage lifecycle management policies causes subsequent archiving and recovery operations to fail. Manage all storage tier settings for Rubrik archiving data through RSC only.

Instant Tiering: RSC supports Azure Instant Tiering, which tiers virtual machine and managed disk snapshots to the configured archival location immediately after each backup completes. When you configure a source retention period of zero days, the primary snapshot is deleted after archiving, eliminating ongoing primary snapshot storage costs. For more information, see Azure instant tiering.

Example: An organization protects 400 Azure virtual machines with daily backups and a 14-day primary retention. Without Instant Tiering, up to 14 primary snapshots for each virtual machine accumulate in managed disk snapshot storage at any given time, generating ongoing primary storage charges across the entire fleet. Enabling Instant Tiering with a source retention of zero days removes primary snapshots immediately after each archiving completes. Snapshots are written directly to the configured access tier archival location and removed from primary storage, reducing primary storage costs to near zero.

Use the AKS Free tier for non-production deployments

RSC supports two AKS cluster tiers for Rubrik-managed Exocompute configurations: Free and Standard (Paid). The Standard tier provides a Microsoft-backed uptime SLA for the AKS control plane and is designed for production workloads where control plane availability is critical. The Free tier offers the same functional capabilities without an SLA and at no additional charge for each cluster. You configure the AKS tier in the advanced Exocompute settings. For more information about the setting and its benefits, see Advanced settings for Exocompute on Azure.

Factor Free tier Standard tier
AKS control plane hourly charge No charge Charged per cluster per hour
Uptime SLA None Microsoft-backed SLA for AKS control plane availability
Suitable for Development, testing, and non-critical Exocompute environments Production Exocompute deployments where control plane availability directly affects backup and recovery SLAs
Important:
Configure the Standard tier for any Exocompute cluster protecting production workloads. A control plane outage in a Free-tier cluster could delay scheduled backups or block time-sensitive recovery operations with no SLA remediation from Microsoft. Use the Free tier only for non-production or evaluation deployments to avoid the per-cluster hourly charge.

For AKS tier pricing, see AKS pricing (Microsoft Azure documentation).

Monitor Azure costs for Exocompute

Use Azure Cost Management and Billing to view the costs associated with your Exocompute environment. Use Cost Analysis and filter by resource group to isolate Exocompute-related charges from other workloads in the same subscription.

When Exocompute launches an AKS cluster, RSC creates resource groups with a Rubrik-Infra prefix. Filtering your cost analysis by this prefix separates Exocompute infrastructure charges from your other Azure workloads. For more information about the resource groups that Exocompute creates, see Set up Exocompute on Azure.

For Exocompute deployments, monitor the following cost categories:
  • Virtual machine compute charges for AKS worker nodes. Virtual machine families vary by workload type. For more information about the virtual machine families that RSC uses, see Exocompute on Azure vCPU quota requirements.
  • AKS Standard tier control plane charges, if the Standard tier is configured
  • Azure Blob Storage charges for archived data, broken down by access tier
  • NAT Gateway data processing and hourly charges, the presence of these charges indicates that blob storage traffic is routing through the NAT Gateway rather than through a service or private endpoint
  • Azure Private Endpoint hourly charges, if private endpoints are configured for blob storage
  • Data transfer charges for traffic leaving the Azure region
Tip:
If Cost Analysis shows ongoing NAT Gateway charges for the resource group containing your Exocompute VNet, verify that a service endpoint or private endpoint is associated with the subnet used by the AKS node pool. Traffic from subnets with no endpoint configured continues to route through the NAT Gateway regardless of other network settings.

For more information about monitoring Azure costs, see Azure Cost Management (Microsoft Azure documentation).
