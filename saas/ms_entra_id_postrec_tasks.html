Post-recovery tasks for Microsoft Entra ID

Recovered Microsoft Entra ID enterprise apps and app registrations can require that you perform manual post-recovery tasks to restore authentication credentials and configurations.

For soft-deleted enterprise apps, RSC restores signing certificates automatically. For soft-deleted app registrations, RSC restores client secrets automatically. Hard-deleted objects require that you manually restore authentication credentials and SSO configurations.

Credentials and SSO

The following table describes the manual steps required after recovering Microsoft Entra ID enterprise apps or app registrations to restore credentials and single sign-on configuration.
Scenario What RSC does What you need to do Location
OpenID Connect (OIDC) client authentication RSC cannot restore client secret values from backups because Microsoft Graph does not return them after creation. Create a client secret in Microsoft Entra ID. Update all external microservices, CI/CD pipelines, daemon services, or key vaults with the new client secret values. For more information, see Add and manage app credentials in Microsoft Entra ID in the Microsoft documentation. Microsoft Entra admin center
SAML single sign-on RSC restores key credentials and token encryption credentials, but cannot restore the original private signing key because Microsoft does not expose private keys through its APIs. RSC accepts an uploaded replacement SAML token signing certificate (.pfx file) or uses Microsoft Graph to generate a new one. RSC outputs the sso_signing_cert_update.csv report listing service principals for which RSC generated a new signing certificate. RSC supports uploading replacement certificates for up to 50 objects per granular restore operation. Generating certificates through Microsoft Graph has no object limit. Download the sso_signing_cert_update.csv report from the RSC restore summary.

If the original signing certificate is not available, provide the new Federation Metadata URL or download the new certificate (Base64) from the restored enterprise app and provide it to each relying party application. Sign-in fails with a signature-validation error until each relying party application receives the updated certificate.

Provide the updated federation metadata to each relying party application at the following URL, replacing tenantID and appID with the values for the restored enterprise app:

https://login.microsoftonline.com/tenantID/federationmetadata/2007-06/federationmetadata.xml?appid=appID

If the original signing certificate (.pfx file) is available, import it into the restored enterprise app and set it as the active token-signing certificate. Relying parties do not require changes.

Verify that the SAML configuration for each app uses the correct default Entity ID (Identifier). For more information, see Configure SAML single sign-on for applications using the Microsoft Graph API in the Microsoft documentation.

In the Microsoft Entra admin center, verify that the primary Identifier (Entity ID) has the Default checkbox selected and that each entry matches a verified domain in the tenant. For more information, see Enable SAML single sign-on for an enterprise application in the Microsoft documentation.

Identifier URIs

The following table describes the manual steps required after recovering app registrations whose Identifier URIs change.
Scenario What RSC does What you need to do Location
Hard-deleted app registration: Identifier URI that references the application ID RSC cannot retain the original application ID of a hard-deleted app registration. The restored app registration receives a new application ID, and RSC changes Identifier URIs of the form api://<oldAppId> to api://<newAppId>. For each client application that uses the old Identifier URI, update the URI to api://<newAppId>. For each client application that uses SAML SSO with an Identifier (Entity ID) of the form api://<oldAppId>, update the Identifier (Entity ID) to api://<newAppId>. Application that uses Microsoft Entra ID for SSO
Cross-tenant recovery: App Registration Identifier URI RSC rewrites Application ID URIs for the target tenant, replacing tenant-specific values with target tenant equivalents based on the domain mappings configured in restore settings. In the Microsoft Entra admin center, verify the Application ID URIs on the recovered app registrations. Update the Application ID URI to the expected value if needed. For more information, see Microsoft Entra ID cross-tenant recovery configuration.

Update any workflows, services, or API clients that validate the original Application ID URI to use the updated value.

 Microsoft Entra admin center: App registrations > [App] > Expose an API

Role assignments and logos

The following table describes the manual steps required to restore app role assignments and custom application logos.
Scenario What RSC does What you need to do Location
Enterprise app role assignments RSC restores app role assignments. If an enterprise app previously had users assigned with default access but has since added explicit app roles, the default access assignment is no longer valid and the restore reports a failure for those assignments. Check the restore summary for failed app role assignments. Manually reassign the correct app role to each affected user or group. Microsoft Entra admin center: Enterprise applications > [App] > Users and groups
Custom application logo RSC does not restore custom application logos. Re-upload the application logo. Microsoft Entra admin center

Home Realm Discovery policies

The following table describes the manual steps required after a cross-tenant recovery that includes Home Realm Discovery policies.
Scenario What RSC does What you need to do Location
Cross-tenant recovery: Home Realm Discovery policy RSC restores Home Realm Discovery policies and applies domain mappings to update the Preferred Domain property. RSC does not configure domain federation in the target tenant. Configure domain federation for the custom domain in the target tenant.

In the recovered Home Realm Discovery (HRD) policy definition, verify that Preferred Domain specifies a verified, federated custom domain.

If Preferred Domain mapped to or fell back to an *.onmicrosoft.com domain, update the Preferred Domain setting. Microsoft does not support federating *.onmicrosoft.com domains, and sign-in acceleration stays inactive until you correct the domain.
