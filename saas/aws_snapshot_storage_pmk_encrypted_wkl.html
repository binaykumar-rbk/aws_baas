Snapshot storage for PMK-encrypted AWS workloads

For AWS workloads, such as EC2 instances and EBS volumes encrypted with a platform-managed key, RSC re-encrypts snapshots using the gateway KMS key when Exocompute tasks such as archiving, indexing, or cross-account replication are configured, and stores the re-encrypted copy as the primary snapshot.

Important:
Setting up Exocompute on AWS applies to the accounts onboarded using the self-managed deployment model only. For the accounts added using the RSC-managed deployment model, Exocompute runs in the infrastructure associated with Rubrik and no VPC or network configuration is required in your AWS account.

AWS encrypts snapshots using either platform-managed keys (PMKs) or customer-managed keys (CMKs). In a centralized Exocompute configuration, the Exocompute account must access snapshots from the source application account to perform tasks, such as archiving, indexing, and cross-account replication. However, AWS prevents cross-account sharing of PMK-encrypted snapshots.

To enable cross-account access, RSC automatically re-encrypts each PMK-encrypted snapshot using the gateway Key Management Service (KMS) key whenever Exocompute tasks are configured in the SLA Domain of the associated workload. Once the copy completes, the re-encrypted version becomes the primary snapshot, and RSC deletes the original PMK snapshot. Performing this re-encryption once at snapshot creation, rather than on-demand for each task, reduces AWS CopySnapshot API calls and eliminates job-level copy contention.

Incremental snapshot behavior after PMK re-encryption

Deleting the original PMK snapshot breaks the AWS incremental CreateSnapshot chain. As a result, the next scheduled backup creates a full snapshot rather than an incremental one. However, the CopySnapshot chain is maintained across re-encrypted copies, so subsequent copy operations are now incremental.

A CreateSnapshot operation completes significantly faster than a CopySnapshot operation for the same snapshot size, for both full and incremental snapshots.

Retention and scale

Configuring a local retention period of at least 1 day enables RSC to perform incremental copies. With a zero-day retention, no previous re-encrypted snapshot is retained, causing every backup to perform a full copy.

Local retention Copy behavior Approximate total data scale limit
0 days Full copy for each backup 150 TB
1 day or more Incremental copy 3,000 TB

Restore behavior

When restoring from a re-encrypted snapshot, the restored volume uses the original encryption key of the workload, not the gateway KMS key used for storage. RSC resolves the original key automatically.

Considerations

For large EC2 instances and EBS volumes using PMK encryption in a centralized Exocompute configuration, the local backup window may be extended. However, overall archival and backup operations complete significantly faster.
