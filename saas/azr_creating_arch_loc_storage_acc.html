Creating a customer-controlled archival location for Azure storage accounts

Create an archival location for the Azure storage account created for archiving the Azure virtual machine or managed disk snapshots and for storing Azure SQL backups.

Before you begin

To use the Private network access option for an Azure archival location, you must meet the following requirements:

  • Private Exocompute cluster: You must use a private Exocompute cluster to provide the secure tunnel required for data transfer. RSC supports the Private storage network option only when you configure a private cluster.

    For more information, see Advanced settings for Exocompute on Azure.

  • Manual endpoint configuration: You must have the necessary permissions in the Azure portal to create private endpoints and link virtual networks.

About this task

Note:
An archival location created for a specific Azure workload is dedicated to that workload, and you cannot use it for other Azure workloads. For example, if you create an archival location to store Azure virtual machine snapshots and link it to an SLA Domain, you can then assign this SLA Domain to the Azure virtual machine. However, you cannot use this same combination of SLA Domain and archival location for Azure SQL or Azure Blob workloads.

Procedure

  1. Log in to RSC.
  2. Click and select Settings.
    The Settings menu appears.
  3. Click Archival & Storage and select Cloud Archival Locations.
    The Cloud Archival Locations page appears.
  4. Click Create Archival Location.
    The Create Archival Location wizard appears.
  5. Select Customer-controlled Archival Location and click Next.
    The Archival Location Region page appears.
  6. In Name, enter a name for the archival location.
  7. In Cloud Provider, select Azure.
  8. In Cloud Account, select the Azure cloud account that you have created for the storage use case.
    If the cloud account is not available, you can add a cloud account using the icon.
  9. Select a region type.
    OptionDescription
    Source region Archives the snapshots to the Azure storage located in the same region as the virtual machines or managed disks. This is a cost-effective option as it involves lower data transfer costs.
    Specific region Archives the snapshots to Azure storage located in a different region.

    Using the Specific region option is more expensive due to the egress charges. Select the Specific region option only if there you need to maintain the snapshot copy in a different region.

    Selecting Specific region enables the Region field.

    Select a region.
  10. Click Next.
    The Storage account details page appears.
  11. For Source region, in Storage Account Prefix, enter a unique prefix string.
    The Storage Account Prefix must contain numbers and lowercase letters only. RSC creates the storage account with the archived snapshots with the prefix entered in Storage Account Prefix.
  12. For specific region, in Storage Account Name, enter a name for the storage account.
    The storage account name must contain numbers and lowercase letters only. RSC creates the storage account for archiving snapshots with the Storage Account Name.
  13. In Container Name, enter a name for the container.
    The container name must start with a letter or number and must contain only lowercase letters, numbers, and the dash (-) character. The Container Name field does not appear if you are using Azure SQL version 2 or later.
  14. Select a storage tier from the following options:
    • Cool
    • Hot
    • Archive
    • Cold
    You cannot use Cold and Archive tier archival locations for Azure SQL backups.
    Note:
    RSC displays a warning if you select a snapshot retention period shorter than the minimum retention period required for a specific storage tier. However, choosing a shorter retention period still incurs charges for the retention period of the selected storage tier.
  15. In Redundancy, select the required redundancy option.
    Azure storage always stores multiple copies of the data to protect it from planned or unplanned events. For more information about the redundancy options, see Azure Storage Redundancy (Microsoft Azure documentation).
  16. In Network Access, select the network access configuration.
    OptionDescription
    All Networks Data flows over the public internet. This option is less secure but requires no additional configuration.
    Specific Virtual Networks (Subnet associated with Exocompute) Data flows over the Azure backbone network through the Exocompute subnet. This option is more secure as you can allowlist only specific VNet and IP addresses, and restrict other VNet and IP addresses. Rubrik recommends using this option as it reduces data transfer costs and keeps traffic within the Azure environment.
    If you select this option, configure one of the following service endpoints for the subnet used by your Exocompute instance:
    • Microsoft.Storage.Global: Required for non-paired cross-region scenarios and also works for same or paired region scenarios.
    • Microsoft.Storage: Required for same or paired region scenarios.
    Private

    Data flows over the Azure backbone network through a secure tunnel. When you select this option, RSC disables public network access for the storage account, ensuring data does not traverse the public internet.

    After creating the archival location, you must configure a private endpoint for the storage account on the Azure portal to ensure connectivity. For more information, see Configuring an Azure private endpoint for storage tiering.

    If this archival location stores Azure SQL Database backups, the private endpoint must include both the blob and table sub-resource types. Configuring only the blob sub-resource, which is sufficient for Azure virtual machine backups, causes Azure SQL Database backups to fail. For more information, see Network configurations for Azure SQL DB.

    To use private storage locations, configure private clusters.

    For detailed information on configuring private clusters, see Advanced settings for Exocompute on Azure.

    If you use public clusters, you must continue to allowlist RSC IP addresses.

    Rubrik recommends using the Private network option.

    Selecting the Private network enables you to skip the manual step of allowlisting RSC IP addresses as these operations will function through the secure tunnel.
  17. Optional: Click Add Storage Account Tag to add key-value pairs for the storage account.
    CAUTION:
    Do not configure lifecycle management policies on the Azure storage account used for this archival location. Lifecycle policies configured outside Rubrik can:
    • Move backup data to the Azure Archive tier, making it inaccessible for recovery.
    • Delete backup data, permanently preventing recovery.
    Rubrik automatically manages cleanup of backup objects — you do not need to create lifecycle policies yourself outside Rubrik to do so.
    Note:
    RSC cannot scan lifecycle policies on Access Key-based Azure accounts. If your storage account uses access key-based authentication, Rubrik recommends switching to Azure Service Principal-based access. For Service Principal-based accounts, update the cloud account permissions under Cloud Accounts to enable lifecycle policy detection.

    If RSC detects harmful lifecycle policies on the storage account during creation, location creation fails. Remove the harmful policies from the Azure storage account and retry.

  18. Click Next.
    The Encryption page appears.
  19. In Encryption Type, select the encryption type for the archival location.
    OptionDescription
    Client-side encryption Encrypts archival data before it leaves the compute environment of the customer and writes to cloud storage. Your keys never leave your systems or network. For more information, see Client-side encryption for Azure virtual machines.
    Server-side encryption with platform-managed key (PMK) Azure encrypts the data at rest using platform-managed keys. All archival data is protected by this encryption type by default.
    Server-side encryption with customer-managed key (CMK) Azure encrypts the data at rest using a key that you manage in Azure Key Vault.
    Important:
    You cannot change the encryption type after you create the archival location.
  20. For client-side encryption, select the key to use as the master key.
    1. In Key Manager, select an Azure Key Vault key manager. For more information, see Adding Azure Key Vaults.
    2. In Key ID, select a key. The field is available after you select a key manager.
    3. In Key Version, select a key version. The field is available after you select a key ID.

    If the Azure subscription linked to the key vault is not mapped to Exocompute, the wizard displays a warning and disables Create. Click Map Exocompute to map the subscription to an Exocompute host, and then continue. For more information, see Mapping Azure accounts to centralized Exocompute.

  21. For server-side encryption with a customer-managed key, select the key vault and key as described in the following steps.
  22. In Key vault, enter or select a key vault.
    If the user-assigned managed identity created by RSC does not have permission to access the selected key vault, then the key vault name appears dimmed. This can happen if the key vault has the vault-based permission model. You need to edit the permission model of a specific key vault to grant access to the user-assigned managed identity created by RSC. The minimum required permissions to access a customer-managed key in Azure Key Vault are wrapkey, unwrapkey, and get.
  23. In Key, select a key for encrypting the data.
  24. Click Create.

Results

RSC creates an archival location for the storage account and stores the keys and connection information.

The archival location appears on the Cloud Native Archival Locations page. The Encryption column shows the encryption type of the location, for example Client-side, Server-side (Customer-managed), or Server-side (Default).

What to do next

To add another layer of protection to a client-side encrypted location, you can rekey the location later.
