Okta cross-tenant recovery

RSC cross-tenant recovery for Okta restores directory objects from a source tenant snapshot to a different onboarded target tenant.

RSC Cross-tenant Recovery (CTR) enables you to restore backed-up Okta directory objects into a separate target tenant. CTR complements same-tenant recovery by providing a safe environment to validate recovery procedures and test configurations without affecting your production tenant.

Cross-tenant recovery use cases

The following scenarios show how you can use cross-tenant recovery:

  • Sandbox and staging validation: You can restore objects into a non-production tenant to verify that recovery jobs run correctly and configurations remain intact before running recovery in your production environment.
  • Disaster recovery: If a source tenant becomes inaccessible or severely compromised, you can restore critical identity objects into a clean, pre-configured target tenant to maintain operational continuity.
  • Integrity testing: You can verify that snapshot data and object relationships restore correctly before running a production recovery drill.
Important:
CTR supports recovery validation and sandbox testing. Rubrik recommends that you do not use cross-tenant recovery as a live migration tool or continuous synchronization method between production tenants.

License compatibility validation

When you select a target tenant for directory object recovery, RSC automatically validates the Okta license tier of the target tenant against the objects in the source snapshot. The validation produces one of three outcomes:

  • Compatible: The target tenant supports the required license tier for all objects in the source snapshot. All objects in the snapshot are available for recovery.
  • Warning: The target tenant has a lower license tier. Objects that require a higher license tier, such as Authorization Servers (Advanced Access Management license) or Entity Risk and Post-Authentication Session Policies (Identity Threat Protection license), are excluded from the object selection screen. You can continue recovery without those objects.
  • Error: RSC cannot reach the target tenant or the credentials that RSC uses for the target tenant have expired. RSC blocks recovery until you re-authenticate or select a different target tenant.

Identity provider credential recovery

When you recover identity providers into a target tenant, RSC handles credentials based on the identity provider type:

  • OIDC, OAuth, and Social identity providers: RSC restores the client secret or private key from the snapshot, so you do not need to re-enter it.
  • Apple identity providers: RSC cannot back up the private key, so the recovered identity provider is Inactive with a placeholder credential. You must enter the private key from Apple in the Okta Admin Console of the target tenant before you activate it.
  • SAML identity providers: RSC restores the external identity provider certificate. Okta generates a new signing key pair in the target tenant. You must download the new public signing certificate from the Okta Admin Console of the target tenant and upload it to the external identity provider.

For details, see Okta identity provider recovery requirements and Authentication settings recovery for Okta objects.

Requirements and limitations

Before you recover objects to a different tenant, review the following topics:
  • Okta cross-tenant recovery configuration: Review the tenant onboarding, permission, license, and credential requirements, and post-recovery domain adjustments.
  • Okta cross-tenant recovery limitations: Review the limitations related to object identity matching, Universal Directory schema dependencies, and supported use cases.
