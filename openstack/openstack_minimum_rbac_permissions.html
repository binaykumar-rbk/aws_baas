Configuring minimum RBAC permissions for OpenStack

Configure the Rubrik integration to use a non-admin OpenStack service account by creating a custom role that grants only the permissions that Rubrik requires.

About this task

This procedure applies to OpenStack Caracal (2024.1) and later. Create a custom role, grant it to the Rubrik service account, and add per-service policy.yaml overrides to allow that role to access only the API endpoints that Rubrik uses. This topic uses rubrik_backup as the example role name.

Procedure

  1. Create a custom role for Rubrik. 
    openstack role create rubrik_backup
  2. Grant the role to the Rubrik service account.

    OpenStack requires two grants on the domain: one inherited grant that covers all projects, and one direct grant that covers domain-scoped authentication.

    # Inherited: project-scoped tokens for every project in the domain
openstack role add \
  --domain <DOMAIN> \
  --user <SVC_ACCOUNT> \
  --user-domain <DOMAIN> \
  --inherited \
  rubrik_backup

# Direct domain: domain-scoped tokens
openstack role add \
  --domain <DOMAIN> \
  --user <SVC_ACCOUNT> \
  --user-domain <DOMAIN> \
  rubrik_backup
    Note:
    The Rubrik client falls back from system scope to domain scope when system-scoped tokens are unavailable. Keystone requires an explicit non-inherited domain assignment to issue a domain-scoped token; the inherited grant alone returns HTTP 401.
  3. For each OpenStack service, append or role:rubrik_backup to the rules listed below in that service's policy.yaml, then reload or redeploy the service.

  4. Optional: If you are using RHOSO 18 (Red Hat OpenStack Services on OpenShift), apply the policy overrides using OpenShift operators instead of editing policy files directly.
    1. For each service, create a ConfigMap with the full policy.yaml content, replacing <existing rule> with the actual defaults for your OpenStack release. 
      oc create configmap cinder-rubrik-policy \
  -n openstack --from-file=policy.yaml=cinder-rubrik-policy.yaml
oc create configmap glance-rubrik-policy \
  -n openstack --from-file=policy.yaml=glance-rubrik-policy.yaml
oc create configmap neutron-rubrik-policy \
  -n openstack --from-file=policy.yaml=neutron-rubrik-policy.yaml
oc create configmap keystone-rubrik-policy \
  -n openstack --from-file=policy.yaml=keystone-rubrik-policy.yaml
    2. Inject the Nova policy using defaultConfigOverwrite. 
      python3 -c "
import json
policy = open('nova-rubrik-policy.yaml').read()
patch = {'spec': {'nova': {'template': {'apiServiceTemplate': {'defaultConfigOverwrite': {'policy.yaml': policy}}}}}}
with open('/tmp/nova-patch.json', 'w') as f: json.dump(patch, f)
"
oc patch openstackcontrolplane openstack -n openstack \
  --type=merge --patch-file=/tmp/nova-patch.json
    3. Inject the Cinder, Glance, Neutron, and Keystone policies using extraMounts, including all existing entries (for example, Ceph mounts).
      Note:
      --type=merge replaces the entire array; omitting existing entries removes them. Rubrik has verified the following propagation types on RHOSO 18: CinderAPI, Glance, Neutron, and Keystone.
    4. Set the policy_file option for Cinder and Keystone so that oslo.policy reads policy.yaml instead of the default policy.json. 
      oc patch openstackcontrolplane openstack -n openstack --type=merge -p '
spec:
  cinder:
    template:
      cinderAPI:
        customServiceConfig: |
          [oslo_policy]
          policy_file = /etc/cinder/policy.yaml
  keystone:
    template:
      customServiceConfig: |
        [oslo_policy]
        policy_file = /etc/keystone/policy.yaml
'
    5. Restart the Cinder, Glance, Neutron, and Keystone pods to apply the updated ConfigMaps. 
      oc delete pod -n openstack -l component=cinder-api
oc delete pod -n openstack -l service=glance
oc delete pod -n openstack -l service=neutron
oc delete pod -n openstack -l service=keystone
      Note:
      Nova restarts automatically when defaultConfigOverwrite changes. The other pods require a manual restart because subPath mounts are not auto-refreshed.

Results

The Rubrik service account now has the minimum required permissions to integrate with OpenStack.

The following table describes how Rubrik uses each permission.

The following table describes how Rubrik uses each permission.
Service Permission Used for
Nova servers:* List, create, start, stop, and delete virtual machines for restore and export
Nova servers:rebuild Rebuild virtual machines during restore
Nova os-volumes-attachments:* Attach and detach Cinder volumes to proxy virtual machines during backup
Nova os-attach-interfaces:* Manage network interfaces on proxy virtual machines
Nova os-keypairs:* List key pairs for VM configuration
Nova os-flavor-extra-specs:index Read flavor extra specs for VM sizing
Nova os-availability-zone:detail Discover availability zones and host topology for environment refresh
Nova os-hypervisors:* Discover compute hosts and register restored virtual machines with the correct host in Rubrik
Cinder volume:get/get_all/create/delete Read, create, and delete volumes for backup and restore
Cinder volume:update Set the bootable flag on restored volumes during export
Cinder volume:*_snapshot Create, read, delete, and revert volume snapshots
Cinder volume:reimage/volume:reimage_reserved Reimage volumes from an image during restore
Cinder volume:attachment_* New Cinder attachment API, used when booting virtual machines from Cinder volumes
Cinder volume_actions:attach/detach/begin_detaching Old attach pipeline, used by Cinder Caracal during snapshot unmount
Cinder volume:*_transfer Cross-project volume transfer
Cinder volume_extension:type_* Read volume types for proper volume creation
Cinder volume_extension:*extra_specs* Read volume type extra specs
Cinder volume_extension:volume_type_encryption:get Read encryption settings during environment refresh
Cinder volume_extension:volume_tenant_attribute Read the tenant attribute of a volume during environment refresh
Cinder volume_extension:volume_host_attribute Read the host attribute of a volume during environment refresh
Cinder volume_extension:volume_mig_status_attribute Read the migration status attribute of a volume during environment refresh
Glance get_image/get_images Discover images for VM inventory
Glance add_image/upload_image/download_image Upload and download proxy VM images
Glance delete_image/modify_image Manage proxy VM images
Glance get_members/get_member/add_member/modify_member Cross-project image sharing for export
Neutron get_network/get_security_group Discover networks and security groups
Neutron create_port/get_port/delete_port/create_port:* Create network ports when booting virtual machines during restore
Keystone identity:list_endpoints/get_endpoint Discover service endpoints for block storage URL resolution
Keystone identity:list_services/get_service Service discovery during onboarding

Rubrik does not require the following admin-level permissions.

The following table describes the admin-level permissions that Rubrik does not require.
Permission Reason not required
os-hypervisors:list as member Exposes infrastructure topology; not for regular project users
os-availability-zone:detail as member Exposes infrastructure topology; not for regular project users
volume_actions:get_all_tenants Rubrik uses per-project scoped tokens; no cross-tenant listing is needed
servers:detail:get_all_tenants Rubrik uses per-project scoped tokens; no cross-tenant listing is needed
backup:* import/export Not used by Rubrik
group:group_types_manage Volume groups are not used
update_volume_admin_metadata Not used by Rubrik

What to do next

After adding the hypervisor policy rules for the first time, run a full environment refresh in Rubrik before you attempt any restores.
